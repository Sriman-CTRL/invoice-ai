# Paivo (invoice-ai)

An AI accounts-receivable (collections) workspace. It turns the slow part of
getting paid — reading customer replies like *"I'll pay Friday"*, *"I already
paid"*, *"the amount is wrong"* — into structured intent + a deterministic next
action, while keeping financial state safe.

**Core safety invariant:** AI output is *advisory only*. It never changes
`invoice.status`. Only real payment records can do that.

## Stack

- **Backend** — Express 5, Prisma 7 (PostgreSQL via `@prisma/adapter-pg`), JWT auth, TypeScript
- **Frontend** — React 18, React Router, Tailwind, Vite
- **AI** — pluggable intent classifier (`IIntentClassifier`): `mock` (rule-based) or `ollama` (local `llama3.2:3b`)

## Quick start

```bash
# 1. Backend
cd backend
cp .env.example .env          # fill in DATABASE_URL + JWT_SECRET
npm install
npx prisma db push            # create the schema (or use prisma migrate dev)
npm run seed                  # loads demo org, customers, invoices, conversations
npm run dev                   # API on http://localhost:5000

# 2. Frontend (separate terminal, repo root)
npm install
npm run dev                   # UI on http://localhost:5173
```

**Demo login** (after `npm run seed`): `demo@ledgerlane.dev` / `demo1234`

## What each screen does

- **Dashboard** — receivables health and collection workload
- **Invoices / Customers / Conversations** — the ledger and the inbox
- **Collection actions** — the work queue generated by classification + overdue rules
- **Try it** — paste a reply, simulate email, create records, run the overdue scan

## Inbound email (the piece that makes the AI reachable)

You never need Gmail OAuth. Give each organization a forwarding address
(`<slug>@<INBOUND_DOMAIN>`), have customers forward replies there, and have your
mail handler POST the parsed email to:

```
POST /api/inbound/email
headers: { "x-inbound-key": "<INBOUND_WEBHOOK_SECRET>" }
body: { to, from, subject, text, html?, invoice_number? }
```

A Cloudflare Email Worker (free) or any forwarder can be shimmed to this shape
in a few lines. The webhook resolves the tenant from the `to` address, finds or
creates the customer, links the invoice, stores the message, classifies it, and
runs the action engine — all in one call.

The authenticated equivalent for the UI is `POST /api/messages/ingest`.

## What's real vs. simulated

| Real | Still simulated / to build |
|---|---|
| Intent classification (mock or local LLM) | Inbound mail transport (MX/forwarder) |
| Deterministic action engine + idempotency | Outbound email/SMS/WhatsApp sending |
| Payment-driven invoice status (row-locked, overpay-guarded) | Invoice PDF generation |
| Multi-tenant scoping (JWT + per-query filters) | Payment links (Stripe/Razorpay/UPI) |
| Overdue detection engine | Accounting integrations (Zoho/Tally/QBO/Xero) |
| Seed data + tests | Queue/cron worker for scheduled actions |

## Key fixes applied (vs. the initial commit)

- Closed two cross-tenant leaks (`GET /customers`, `GET /organizations`)
- Payment status is now server-validated; only `SUCCEEDED` moves invoice status;
  the invoice row is locked (`FOR UPDATE`) to prevent concurrent over-payment
- JWT secret is fail-closed (no silent dev fallback)
- Rate limiting on auth and inbound webhook
- Confidence threshold routes low-confidence classifications to `MANUAL_REVIEW`
- DB indexes, pagination + total-count headers on list endpoints
- Seed script, `.env.example`, unit tests, and this README

## Environment variables

See `backend/.env.example` for the full annotated list. The required ones:

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | PostgreSQL connection string |
| `JWT_SECRET` | **Required** — signing secret |
| `CLASSIFIER` | `mock` or `ollama` |
| `AI_CONFIDENCE_THRESHOLD` | below this → human review (default `0.75`) |
| `INBOUND_WEBHOOK_SECRET` | **Required** to enable `POST /api/inbound/email` |
| `INBOUND_DOMAIN` | domain for per-org forwarding addresses |
